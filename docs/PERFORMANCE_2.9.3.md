# 2.9.3 화면 부하 측정

측정일: 2026-11-18. 같은 Mac에서 2.9.2 기준 빌드와 2.9.3 최종 빌드를 비교했습니다.

## 조건

- 실제 앱의 `ContentView`, `AppModel`, 전사 카드와 AI 도움창을 사용했습니다.
- 가상 발언 1,000개를 먼저 넣고, 초당 2회 발언 추가와 초당 8회 음량·시간 갱신을 수행했습니다.
- 임시 저장소에서 5초 준비 후 약 20초를 측정했습니다. 각 버전 3회 실행의 중앙값을 비교했습니다.
- 1440×850 크기의 비표시 `NSHostingView`에서 화면 배치와 메인 이벤트 처리를 실행했습니다. Swift 최적화 빌드를 사용했고, 측정 시 컴파일 작업은 완료된 상태였습니다.
- 음성 인식 엔진·마이크·외부 AI 호출은 별도 측정 범위입니다. 이번 수치는 화면 처리 비용을 나타냅니다.

별도 샘플 앱의 화면 제어 연결이 중단되어 비표시 실행으로 측정을 진행했습니다. 초기 이미지 캡처 반복 실험에서는 CoreGraphics 이미지 복사 비용이 크게 잡혔습니다. 최종 비교는 화면 배치 경로를 측정하고, 화면 확인용 PNG를 측정 종료 후 한 번 생성했습니다.

## 결과

| 지표 | 2.9.2 | 2.9.3 | 변화 |
|---|---:|---:|---|
| CPU, 코어 1개를 100%로 환산 | 15.51% | 9.93% | 약 36% 감소 |
| 전사 갱신·동기 화면 배치 시간, p95 | 53.81ms | 46.26ms | 약 14% 감소 |
| 16ms 메인 타이머의 실제 간격, p95 | 24.66ms | 21.27ms | 약 14% 감소 |
| 실행 중 최대 상주 메모리, 중앙값 | 108.69MiB | 112.42MiB | 약 3.4% 증가 |

CPU 사용량은 2.9.2에서 15.31~17.63%, 2.9.3에서 9.57~10.23%였습니다. 메모리는 비슷한 범위를 유지했으며, 이번 변경의 확인된 이점은 CPU와 반복 화면 배치 비용 감소입니다.

메인 타이머의 최대 간격은 실행별 편차가 있었습니다. 2.9.2는 71.92~81.28ms, 2.9.3은 63.08~113.02ms였으며, 최종 버전의 세 실행 중 한 번에서 100ms 초과 간격 한 개를 관측했습니다. p95는 각 실행의 95백분위수를 구한 뒤 세 실행의 중앙값으로 요약했습니다. 이 타이머는 이벤트 처리 지연 지표이며 화면 프레임률과 구분합니다.

실제 장시간 녹음의 총 CPU·메모리는 음성 모델, 회의 자료, AI 작업과 함께 측정해야 합니다. 이번 샘플 결과의 적용 범위는 위 조건의 화면 처리입니다.

## 적용한 변경

- 최근 발언 카드 60개를 우선 표시하고, 이전 발언은 60개씩 펼칩니다. 읽던 구간과 전체 저장·편집 데이터는 유지합니다.
- 발언 묶음과 전사 표기 변환 결과를 재사용합니다. 카드의 문장·화자·원본 편집 대상이 같으면 카드 계산 결과를 유지합니다.
- 음량 막대 24개의 개별 애니메이션을 하나의 `Canvas` 그리기로 바꿨습니다.
- 2.9.2에서 적용한 음량·시간 관찰 범위 분리, 전사 표시 요청 병합, 긴 발언의 표시 분할을 유지합니다.

## 재현

프로젝트 루트에서 설치 앱을 기반으로 측정용 앱을 만듭니다. 원본 회의 파일은 읽기 전용으로 유지하며, 샘플 데이터는 임시 저장소에 생성합니다.

```bash
sample_app="$(bash Verification/build-performance-app.sh)"
"$sample_app/Contents/MacOS/TableLog" --headless
```

측정용 앱과 같은 임시 폴더에 `performance-result.json`, `performance-preview.png`가 생성됩니다. 빌드가 끝난 뒤 같은 실행 파일을 반복 실행해 비교할 수 있습니다.
